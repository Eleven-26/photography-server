# RBAC 运维手册

> 面向开发与运维的日常操作手册：如何新增权限点、缓存如何刷新、403/数据不可见如何排查。
> 概念与权限点清单见同目录[《权限点手册》](./权限点手册.md)。

## 一、新增权限点流程（后端 → 数据库 → 前端）

以"新增 `order:export`（导出订单）"为例：

**① Go 常量**：`internal/domain/perm.go`

```go
// 常量区
PermOrderExport Perm = "order:export"

// permGroups 的对应模块内归类（勿遗漏，否则前端配置树看不到）
{PermOrderExport, "导出订单"},
```

**② 路由挂载**：`internal/router/router.go`（或员工端 `internal/presentation/wechat/staff.go`）

```go
o.POST("/export", mw.Perm(domain.PermOrderExport), ctl.ExportOrders)
```

**③ 字段级校验（可选）**：同一接口内不同字段对应不同权限点时，在 service 里用
`s.requirePerm(op, domain.PermOrderExport)`。

**④ SQL 种子（三步铁律）**：

1. 写增量：`docs/sql/增量/upgrade_role_permission_YYYYMMDD.sql`，INSERT 格式与既有种子一致
   （`JOIN sys_role ON code`，不写死 role_id）；
2. 合并进全量：同步修改 `docs/sql/dml.sql` 对应段落（并核对文件头注释的角色数量统计）；
3. 实跑校验：`bash docs/sql/verify_consistency.sh`（需 Docker mysql-dev 运行），
   必须三视图零差异。

**⑤ 前端映射**（photography-frontend）：

- 页面入口：路由 `meta.perm`（`src/router/index.ts`）；
- 按钮：`v-perm="'order:export'"`；
- 逻辑分支：`auth.hasPerm('order:export')`。

**⑥ 回归**：后端 `go build ./... && go vet ./... && go test ./internal/...`；
前端 `npx vue-tsc --noEmit && npm run build`。

**⑦ 发布后生效**：管理员在「设置 → 角色 → 权限配置」勾选保存即可（保存动作主动清缓存，
见第二节；`admin` 角色无需勾选，天然全量）。

## 二、缓存机制与刷新

两层缓存（`internal/pkg/authcache`）：

| 缓存 | Key | TTL | 内容 |
|---|---|---|---|
| 员工画像 | `auth:staff:{userID}` | 60s | 角色归属/门店/停用状态 |
| 角色授权 | `perm:role:{companyID}:{roleID}` | 30min | role_code、data_scope、权限点集合 |

**主动失效时机**（`invalidateRoleAuth`，代码即刷新，无需手工干预）：

- 角色创建 / 角色更新（`role/create`、`role/update`）；
- 角色授权保存（`role/grant/:id`，data_scope 与权限点同事务写入后失效）。

因此权限/数据范围变更**即时生效**（受 60s 画像缓存影响，最迟约 1 分钟）；前端 permissions
随登录/Profile 返回，刷新页面即拿到新权限。

**手工清缓存**（仅排障用）：

```bash
docker exec -i redis-dev redis-cli DEL "perm:role:1:5"   # 清指定角色授权
docker exec -i redis-dev redis-cli DEL "auth:staff:123"  # 清指定员工画像
```

**降级语义**（排障时须知）：

- Redis 不可用 → 直查 DB（fail-open，功能不受损）；
- 角色查不到 → 空权限（fail-closed，仅 admin 短路可通行）。

## 三、403 排查路径

按顺序定位，绝大多数问题停在前两步：

1. **查角色是否有点**：

   ```sql
   SELECT rp.permission FROM sys_role_permission rp
   JOIN sys_role r ON r.id = rp.role_id
   WHERE r.company_id = ? AND r.code = '?';
   ```

   没有该权限点 → 在「角色权限配置」勾选保存，或走第一节流程补种子。
2. **查用户角色**：`SELECT role_id FROM sys_user WHERE id = ? AND deleted = 0;`
   角色被改过/被停用 → 画像缓存最长 60s 自动过期。
3. **查缓存**：`GET perm:role:{cid}:{rid}`，与 DB 结果不一致 → DEL 后重试（正常不应出现，
   出现说明失效调用被绕过，排查是否直写 DB）。
4. **查路由挂点**：该接口挂的权限点与前端请求的是否同一个（详见 `.doc/_rbac_matrix.txt`
   角色 × 路由矩阵）。常见坑：接口拆分后两个动作共用了同一个权限点。
5. **员工端**：小程序前端尚未接入 hasPerm/403 处理，被拦时表现为接口报错而非友好页面（已知遗留）。

## 四、数据不可见排查

用户"登录正常但列表为空/少数据"时，按数据范围口径排查：

1. **查角色的 data_scope**：`SELECT code, data_scope FROM sys_role WHERE company_id = ?;`
   （1 全部 / 2 本门店 / 3 仅本人）。
2. **查操作人门店**：`SELECT store_id FROM sys_user WHERE id = ?;`
   本店用户 `store_id = 0` 会**降级为仅本人**——先怀疑没分配门店。
3. **查数据归属列**：订单类看 `store_id` / `photographer_id` / `owner_id` 是否命中；
   收款/退款/加项/改期/评价/交付经**订单可见性**间接过滤（先看对应订单可见否）。
4. **无操作人上下文的链路恒为全量**：客户侧 H5、定时任务、单元测试不受数据权限影响，别在这里找"越权"。

## 五、SQL 脚本维护规范

详见 `docs/sql/README.md`，要点：

- **不变量**：全量一次执行 == 增量链按序执行，任何改动后必须实跑 `bash docs/sql/verify_consistency.sh`；
- 权限绑定种子**只认** `docs/sql/增量/upgrade_role_permission_20260910.sql`（历史草稿已删除，
  勿再引用 `.doc/` 下的旧种子）；
- 字符集统一 `utf8`；禁止格式化 `USE \`photography\`;` 行（拆行会导致整库初始化失败）。

## 六、验证与回归清单

上线/改动后建议回归范围（4 角色 × 2 端）：

| 检查项 | 操作 |
|---|---|
| admin 全量回归 | 登录 admin，各菜单/按钮全部可用 |
| photographer 工作流 | 员工端登录：线索跟进、现场加项、收款凭证、工作室设置 4 项（2026-09-11 补点后应全部可用） |
| manager 数据范围 | 只能看到本门店订单与其从表数据 |
| sales 数据范围 | 本门店客户/线索可见，交接场景（客户改 owner 后新销售可见） |
| 权限变更时效 | 角色勾选保存后 ≤1 分钟内，该角色用户刷新页面生效 |
| 配置页 | 「设置 → 角色」数据范围三档切换 + 分组勾选树保存回读一致 |
