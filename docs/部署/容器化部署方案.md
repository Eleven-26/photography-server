## 一、部署拓扑

### 1.2 请求链路

```
浏览器 / 微信内
      │
      ├─ :8081 ─→ frontend  ─┐
      ├─ :8082 ─→ h5        ─┤  nginx（容器内 80）
      └─ :8083 ─→ wechat    ─┘       │
                                     │  /api/xxx → 剥掉 /api
                                     ▼
                              backend:8080/xxx
                                     │
                                     ▼
                    mysql / redis / nats / nacos / …
```

三个前端站点结构**完全一致**：nginx 托管静态产物 + `/api` 剥前缀反代 `backend:8080`。前端一律请求 `/api/...`，后端真实路由*
*不含** `/api`。

### 1.3 网络隔离

- `frontend-net`：三个前端站点 + `backend`
- `backend-net`：`backend` + 全部基础设施

站点容器**只能**访问 `backend`，碰不到数据库、Redis、Nacos。隔离由 Docker 网络实现，不依赖防火墙规则。

### 1.4 依赖分层与一键启动

`depends_on` 只能表达"进程级"与"就绪级"依赖；本项目缺的是**数据级**依赖
（Nacos 里有 `data_id`、MySQL 里有表、Nacos 里有管理员）——它描述数据状态而非进程状态，
compose 无论怎么写都等不到。补齐方式是给它找一条**可等待的路径**：

| 阶段 | 服务 | 等待条件 |
|---|---|---|
| ① 基础设施 | `mysql` / `redis` / `nats` | 无依赖；`mysql` 首启执行 `/docker-entrypoint-initdb.d/` 建三个库与全部表 |
| ② 元数据服务 | `nacos`、`xxl-job-admin` | `mysql: service_healthy` |
| ③ 数据初始化 | `nacos-init` | `nacos: service_healthy`；**退出码 0** |
| ④ 应用 | `backend` | `nacos-init: service_completed_successfully` + 四个基础设施 `service_healthy` |
| ⑤ 前端站点 | `frontend` / `h5` / `wechat` | `backend` 已启动 |

因此 `docker compose up -d` 一条命令即可覆盖**首次部署与日常启动**。
细节、验证清单与常见问题见 [`README.md`](README.md)。

## 二、两形态说明（核心）

### 2.1 一句话结论

> **`wechat` 服务是一个生产可访问的独立站点，不是占位、不是为凑拓扑图好看。**

它与 `h5` 服务是**同一级别**的真服务，宿主端口 8083，浏览器 / 手机浏览器 / 微信内打开都能直接使用——查订单、审改期、确认到账、看通知，功能齐全。

### 2.2 为什么会有「wechat 容器不访问」的误解

误解来自一句正确但容易被断章取义的话：

> 「微信小程序形态由微信开发者工具上传，不走容器。」

这句话**只针对小程序形态**。而 `photography-wechat` 是 **uni-app 双端工程**，一份源码能编译出两个产物：

| 编译命令                      | 产物目录                   | 去向                 | 是否经容器  |
|---------------------------|------------------------|--------------------|--------|
| `npm run build:h5`        | `dist/build/h5`        | **nginx 容器**（8083） | ✅ 经容器  |
| `npm run build:mp-weixin` | `dist/build/mp-weixin` | **微信开发者工具**上传      | ❌ 不经容器 |

两者是**同一份代码的两个形态，都真实存在、都能用**，不存在「哪一个是假的」。

```
                 photography-wechat（uni-app Vue3 源码 · 只有一份）
                                  │
              ┌───────────────────┴───────────────────┐
              ▼                                       ▼
      npm run build:h5                    npm run build:mp-weixin
              │                                       │
      dist/build/h5                        dist/build/mp-weixin
              │                                       │
      nginx 容器 · 8083                    微信开发者工具上传
              │                                       │
    浏览器 / 微信内直接打开                     微信小程序 · 不走容器
              │                                       │
              └────────── 两条都真实可访问 ───────────┘
```

### 2.3 当前实际状态：小程序形态**尚未启用**

两个客户端仓的 `src/manifest.json` 中，小程序 `appid` 目前**都是空字符串**：

```jsonc
// photography-h5/src/manifest.json
"mp-weixin": { "appid": "", ... }

// photography-wechat/src/manifest.json
"mp-weixin": { "appid": "", ... }
```

也就是说——**小程序形态目前根本没有注册、没有上传、跑不起来**。当前唯一能真正打开使用的，恰恰就是容器里那两个 H5 站点。

> 这一点足以证伪「容器是占位」：如果 `wechat` 容器只是占位，那这套系统现在**没有任何员工端可用**。

### 2.4 两个形态为什么要都保留

不是冗余，是场景互补：

| 维度   | H5 形态（容器）      | 小程序形态（微信工具）  |
|------|----------------|--------------|
| 上线门槛 | 无需审核，构建即可用     | 需注册主体、提交审核   |
| 访问方式 | 链接 / 二维码，任意浏览器 | 只能微信内，需搜索或扫码 |
| 分享能力 | 链接可外发给任何人      | 链接分享受限       |
| 原生能力 | 受浏览器限制         | 可调更多微信原生能力   |
| 发版周期 | 分钟级（重建容器）      | 审核周期，不可控     |
| 联调便利 | 服务器改完重建即可看     | 需上传 + 真机预览   |

**实用状态**：小程序在注册 / 审核期间，H5 站点照常给摄影师使用；小程序上线后两者并存。

对称地，`photography-h5` 仓同样具备编译成小程序的能力（`build:mp-weixin` 脚本齐全，appid 也是空），只是业务上没有这个需求。

### 2.5 常见误解速查

| 说法                        | 正误                                  |
|---------------------------|-------------------------------------|
| 「h5 容器是要访问的」              | ✅ 对                                 |
| 「wechat 容器不访问，放着只为补齐编排拓扑」 | ❌ **错**。它是员工端 H5 站点，8083 真实可访问      |
| 「真正要访问的代码是微信开发者工具上传的那份」   | ⚠️ 半对。小程序形态确实走微信工具，但它不是「唯一真实」的，两者都是 |
| 「微信小程序和 H5 站点是同一份代码」      | ✅ 对。同一份源码，两种编译目标                    |

## 三、两仓 Docker 构建链

两仓结构一致（仅在注释与上传说明上区分端）：

| 文件                 | 作用                                                      |
|--------------------|---------------------------------------------------------|
| `Dockerfile`       | 两阶段：`node:20-alpine` 编译 → `nginx:1.27-alpine` 托管        |
| `build/nginx.conf` | 静态托管 + `/api/` 剥前缀反代 `backend:8080` + 缓存策略              |
| `.dockerignore`    | 排除 `node_modules` / `dist` / `unpackage` / `.workbuddy` |

**构建阶段要点**

1. **产物路径**：uni-app 的 H5 输出在 **`dist/build/h5`**（H5 平台目录），**不是** `dist` 根。`COPY` 源写错会得到一个空白站点。
2. **alpine 适配**：构建阶段装 `libc6-compat`，否则 musl 下部分依赖的原生二进制不可用。
3. **上传上限**：`client_max_body_size 100m`，与后端 prod 的 `upload.max_size_mb=100` 对齐。默认 1M 会让客户传付款凭证、员工传样片直接
   413。

## 四、部署目录约定

compose 中 `./photography-{server,frontend,h5,wechat}` 这类相对路径，**只有把各仓平级放在同一父目录、并把 compose
文件放在该父目录时才成立**：

```
/opt/slot/
├── docker-compose.yml        ← 从 photography-server 复制
├── .env                      ← 从 photography-server 复制
├── volume/                   ← 数据卷目录（自动创建）
├── photography-server/
├── photography-frontend/
├── photography-h5/
└── photography-wechat/
```

> ⚠️ 本例中 `context` 是**相对 compose 文件**解析的（非相对 CWD）。
> 因此本机直接 `cd photography-server && docker compose build` 必然失败（找不到 context）。
> 本机验证需显式指定父目录：
>
> ```bash
> docker compose --project-directory "D:/www" \
>   -f "D:/www/photography-server/docker-compose.yml" build h5 wechat
> ```

## 七、已知限制与待办

1. **镜像构建未实测**：Docker daemon 未启动，仅完成静态校验。首次部署前建议先 `docker compose build h5 wechat` 验证。
2. **PC 管理端 nginx 缺上传上限**：`photography-frontend/build/nginx.conf` 未设 `client_max_body_size`（nginx 默认
   1M），后台上传作品大图会 413。**本次未改，待补**。
3. **小程序形态未启用**：两仓 `mp-weixin.appid` 均为空，需业务侧在微信公众平台注册后填入才可上传。
4. **两条链路通道需二选一**：SkyWalking native 与 OTel→Jaeger 同开会产生双 span / 双上报。
5. **一键启动改造尚未端到端实测**：compose 语法、依赖声明、initdb 挂载与 Go 编译均已验证，
   但完整 `docker compose up -d`（首次建三个库 → Nacos 就绪 → 管理员初始化 → 配置发布 → backend 起）
   需要在有 Docker daemon 的机器上跑一次；探针里 `nacos` 的候选端点（`/nacos/v1/console/health/readiness`
   优先）也需实跑确认哪个在该版本可用。
6. **`xxl-job-admin` 探针可靠性未验证**：该镜像内是否带 `curl`/`wget` 未确认，探针可能恒为 unhealthy；
   已确保它**不阻塞 backend**（等待条件仍是 `service_started`），可按需删除该 healthcheck。
